## 这是自动的

当前模型来自一个订阅的话，服务端的限流信号会带重置时间。Cetas 收到信号就记下这个时间，到点自动恢复工作——没有闹钟要设，没有"稍后再试"要你记着，更不用盯着屏幕等。

边界也照实说：前提是 Cetas 还开着、session 没有切换。等的时候你走开、睡觉、干别的都行；把进程关了或换了 session，恢复就无从谈起。

## 凌晨三点，没有人守着

没有守卫的长任务死在一个很蠢的地方。跑到第 90 分钟，供应商回一个 429，agent 说"配额用尽，稍后再试"，然后这条消息在第二天早上才被看到。五个小时白等，任务还得重讲一遍。守卫把"稍后再试"变成它自己的事。

不带重置时间的限流（多数按量计费的 API key 是这种），按退避节奏去探，封顶不硬敲。你睡你的觉。

## 等待不丢工作

等可以，前提是醒来之后一切还在。失败的那一轮先落盘，会话才被标记为可恢复，顺序反了，恢复时拿到的就是残缺的上下文。它等的时候你在做别的，它续的时候任务接着跑、历史接着写，不需要你重述任何东西。

## 你需要它吗

三个问题自查：

- 跑过超过一小时的任务吗？
- 供应商按 5 小时窗口计额度，任务经常跨窗口吗？
- 设过闹钟回来重发任务吗？

有一条命中，它就值得先配上。一条都没有，暂时用不上，装了也不会碍事。

## 两件事它不做

撞限流时它不会自作主张换供应商或换模型，想换是 `/model quick-pick` 的事，两个机制各管各的。反复失败到次数上限，它停下来把结论交给你，不会整夜敲门。
